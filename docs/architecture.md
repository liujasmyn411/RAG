## 三、模块职责

### 3.1 API 网关层 (`app/api/`)

- **职责**：HTTP 协议转换，请求/响应格式化，路由分发
- **关键文件**：
  - `app/api/v1/chat.py` —— 林黛玉 Agent 对话接口（SSE 流式）
  - 未来扩展：`students.py`, `scores.py`, `employments.py`, `auth.py`
- **设计原则**：
  - 路由 handler 只负责：校验参数、注入依赖、调用 Service/Agent、返回响应
  - 不包含任何业务逻辑

### 3.2 Agent 编排层 (`app/agents/`)

- **职责**：AI Agent 的核心决策循环，决定何时调用工具、如何组织回答
- **关键文件**：
  - `app/agents/lin_daiyu/agent.py` —— ReAct 主循环（手动解析 Action）
  - `app/agents/lin_daiyu/prompts.py` —— 系统 Prompt 加载与渲染
  - `app/agents/lin_daiyu/memory.py` —— Session 级对话历史管理
  - `app/agents/tools/registry.py` —— 工具注册装饰器
  - `app/agents/tools/classic_search.py` —— 四大名著检索工具
  - `app/agents/tools/student_query.py` —— 学生信息查询工具
- **设计原则**：
  - Agent 只认识"工具"，不认识具体的数据库表
  - 所有数据源（MySQL/Milvus）都封装为统一接口的 Tool
  - Prompt 与代码分离，模板化存储（`prompts/lin_daiyu_system.md`）

### 3.3 Service 业务层 (`app/services/`)

- **职责**：封装业务逻辑，处理数据聚合、统计计算、权限过滤
- **关键文件**：
  - `app/services/student_service.py` —— 学生/成绩/就业/统计查询
  - `app/services/knowledge_base.py` —— Milvus 向量检索封装
- **设计原则**：
  - Service 层不知道 HTTP，只接收参数、返回数据
  - 复杂查询（如统计报表）在 Service 层用 SQL 或 ORM 实现
  - 未来可按模块拆分：`student_service.py`, `class_service.py`, `teacher_service.py`

### 3.4 数据访问层 (`app/models/`)

- **职责**：ORM 模型定义、数据库连接管理、Session 生命周期
- **关键文件**：
  - `app/models/database.py` —— SQLAlchemy 引擎和 Session
  - `app/models/entities/*.py` —— 9 张表的 ORM 模型
- **设计原则**：
  - 一张表一个文件，清晰可维护
  - 外键关系在 ORM 层定义，便于 JOIN 查询

## 四、核心数据流

### 4.1 学生成绩查询（带 Agent）

```
用户提问
    │ "查一下学生 1001 的成绩"
    ▼
FastAPI POST /api/v1/lin-daiyu/chat
    │
    ▼
Agent 主循环
    │
    ├──▶ 构建 messages (system + history + user)
    │
    ├──▶ 调用 LLM (第一轮，非流式)
    │       │
    │       └──▶ 通义千问 API
    │               │
    │               └──▶ 返回 ReAct 格式文本
    │                       Thought: ...
    │                       Action: query_student_score
    │                       Action Input: {"student_no": "1001"}
    │
    ├──▶ 解析 Action
    │       │
    │       └──▶ Tool Registry 执行 query_student_score
    │               │
    │               └──▶ StudentService.get_scores_by_student_no()
    │                       │
    │                       └──▶ MySQL SELECT ... WHERE student_no = '1001'
    │                               │
    │                               └──▶ 返回: 第一次月考 85分, 第二次月考 78分
    │
    ├──▶ Agent 将结果加入历史 (Observation)
    │
    ├──▶ 调用 LLM (第二轮，流式)
    │       │
    │       └──▶ 通义千问 API
    │               │
    │               └──▶ 返回: "那1001号学生的功课么……"
    │
    └──▶ SSE 流式输出给前端
            │
            ├── event: thinking
            ├── event: tool_call
            ├── event: tool_result
            ├── event: message (打字机效果)
            └── event: done
```

### 4.2 四大名著知识问答

```
用户提问
    │ "红楼梦里黛玉葬花是怎么回事？"
    ▼
Agent 主循环
    │
    ├──▶ 调用 LLM 第一轮
    │       └──▶ 返回 Action: search_classic_literature
    │
    ├──▶ Tool 执行
    │       └──▶ KnowledgeBase.search_classic()
    │               │
    │               ├──▶ BGE 模型编码查询向量
    │               │
    │               └──▶ Milvus 语义检索 (Top-K)
    │                       │
    │                       └──▶ 返回《红楼梦》相关段落
    │
    ├──▶ 结果加入历史
    │
    └──▶ LLM 第二轮生成黛玉口吻回答
            └──▶ SSE 流式输出
```

## 五、数据库架构

### 5.1 实体关系

```
users (统一认证)
  │── user_type='teacher' ──▶ teachers (老师详情)
  │── user_type='student' ──▶ students (学生详情)
  └── user_type='admin' ────▶ (无详情表，纯管理账号)

teachers ──┬── headteacher ──▶ classes (班级)
           └── instructor ───▶ classes (班级)

classes ◄─── N:1 ─── students (学生所属班级)

students ◄─── 1:N ─── scores (学生成绩)

students ◄─── 1:1 ─── employments (学生就业)
```

### 5.2 关键约束

| 约束 | 表 | 字段 | 说明 |
|------|-----|------|------|
| 唯一 | users | username | 登录账号唯一 |
| 唯一 | teachers | teacher_no | 工号唯一 |
| 唯一 | students | student_no | 学号唯一 |
| 唯一 | classes | class_no | 班级编号唯一 |
| 联合唯一 | scores | (student_id, exam_seq) | 一个学生同一序次一条成绩 |
| 唯一 | employments | student_id | 一个学生一条就业记录 |

## 七、关键设计决策

### 7.1 为什么用手动 ReAct 而不是原生 Function Calling？

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 原生 Function Calling | 模型自动决策，结构清晰 | 通义千问兼容模式不稳定，常不触发 tools | ❌ 弃用 |
| **手动 ReAct** | 兼容所有模型，可控性强，Prompt 示例直接指导输出 | 需要解析文本中的 Action | ✅ **采用** |

### 7.2 为什么就业表是一对一而不是一对多？

- **当前需求**：只管理学生"当前"的就业状态
- **业务场景**：培训机构关注学生是否已就业、薪资多少，不追踪跳槽历史
- **扩展性**：如需改为一对多，只需去掉 `student_id` 的唯一约束即可

### 7.3 为什么 users 表用 ref_id 而不是多个外键字段？

- 一个用户只能是老师、学生或管理员之一，不会同时是多种角色
- `ref_id` + `user_type` 组合比 `teacher_id` / `student_id` / `advisor_id` 三个可空字段更简洁
- 程序层负责维护一致性，查询时根据 `user_type` 路由到对应详情表

### 7.4 为什么 Session 记忆先用内存而不是 Redis？

- **当前阶段**：单实例部署，内存足够
- **未来扩展**：`SessionMemory` 已抽象为类，替换为 Redis 只需改 `memory.py` 一个文件
- **限制**：应用重启后会话丢失，但演示和开发阶段可接受
