### 1.2 核心约束

- **事实准确性 > 人格一致性**：不能为了维持人设不顾事实
- **技术栈**：LangGraph + Neo4j + Milvus + PostgreSQL
- **特色资源**：四大名著向量库、红楼梦人物图谱
- **成本策略**：允许额外 LLM 调用用于记忆整理和风格校准

### 2.3 压缩策略

```
                    每轮对话结束
                         │
                         ▼
                ┌─────────────────┐
                │ 滑动窗口 ≥ 10 轮？│
                └────────┬────────┘
                         │
              ┌──────────┴──────────┐
              │ 否                   │ 是
              ▼                      ▼
         ┌────────┐        ┌─────────────────┐
         │ 保留全部 │        │ 语义触发判断      │
         │ 不做压缩 │        │ (小模型判断价值)   │
         └────────┘        └────────┬────────┘
                                    │
                         ┌──────────┴──────────┐
                         │ 有价值               │ 无价值/教务
                         ▼                      ▼
                  ┌────────────┐        ┌────────────┐
                  │ 生成摘要    │        │ 跳过摘要    │
                  │ 插入头部    │        │ 仅保留最近  │
                  └────────────┘        │ 1 次查询结果 │
                                        └────────────┘
```

**压缩规则汇总**：

| 数据类型 | 保留策略 | 例外 |
|---|---|---|
| 日常闲聊 | 10轮窗口 + 摘要 | — |
| 教务查询 | 不摘要，仅保留最近 1 次结果 | — |
| 心理危机 | 永久保留，不参与压缩 | 安全熔断最高优先级 |
| 业务数据 | 仅最近 1 次查询结果 | 不跨轮次持久化 |

### 2.4 安全熔断层详细设计 (扩展后)

原有的 Layer 0 仅覆盖"心理危机"一种场景。面向学生的 Agent 需要更完整的安全体系。

#### 2.4.2 检测机制：两级过滤

```
用户消息到达
      │
      ▼
┌──────────────────┐
│ 第一级: 关键词+   │ 毫秒级, 不需要 LLM
│ 正则规则过滤      │
│                  │
│ · 已知敏感词库   │
│ · 脏话/侮辱词库  │
│ · Prompt注入模式 │
└────────┬─────────┘
         │
    ┌────┴────┐
    │ 命中     │ 未命中
    ▼          ▼
┌────────┐  ┌──────────────────┐
│ 直接    │  │ 第二级: LLM 语义  │ ~200ms, 小模型
│ 进入    │  │ 安全判断          │
│ 处理    │  │                  │
│ 流程    │  │ 判断消息是否包含:  │
└────────┘  │ · 政治敏感        │
            │ · 侮辱/歧视       │
            │ · Prompt注入      │
            │ · 骚扰/霸凌       │
            │                  │
            │ 输出 JSON:        │
            │ {risk_level,     │
            │  category,       │
            │  confidence}     │
            └────────┬─────────┘
                     │
                     ▼
              ┌──────────────┐
              │ 按分级处理    │
              └──────────────┘
```

**为什么需要两级？**
- 第一级拦截已知模式（毫秒级），避免让敏感内容流入 LLM 上下文
- 第二级处理变体/隐晦表达，关键词无法穷举

#### 2.4.3 B1 政治敏感：分级处理 + 用户状态标注

```
┌──────────────────────────────────────────────────────────────┐
│  B1 政治敏感 (零容忍, 无渐进累积)                              │
│                                                              │
│  Level 1 (轻度 — 擦边提及):                                    │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  behavior: 不直接回应敏感部分, 转移话题                    │  │
│  │  response (黛玉): "这些事不是我们该议论的。你且说些别的罢。" │  │
│  │  response (非黛玉): "这个问题不在我的回答范围内。"          │  │
│  │  memory: 不入库 (L3 跳过提取)                             │  │
│  │  log: 记录 anonymized 安全事件                            │  │
│  │  user_label: safety_status = "flagged_low"             │  │
│  │  action: 不计违规, 不下沉用户状态                         │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  Level 2 (中度 — 明确敏感话题):                                │
```

### 2.5 跨会话 State 继承机制

当会话因超时、显式结束或长时间中断而关闭后，下一次学生发消息时，需要根据 `carry_over_level` 初始化新的 State。核心问题是：**上次会话的什么内容、以什么形式、带到新会话中去。**

#### 2.5.1 会话关闭时的归档流程

会话关闭时必须同步生成归档包——不能依赖 Reflection（异步、不确定触发时间），下次会话可能在 Reflection 之前就启动了。

#### 2.5.4 rolling_summary 的演化

每次会话关闭时，将本次摘要与旧摘要合并蒸馏，始终只保留一个浓缩版本：

```
本次会话摘要 + 旧 rolling_summary
           │
           ▼
      LLM 合并蒸馏:
      · 旧会话细节逐渐被压缩
      · 稳定的认知 (如"数学偏弱") 持续保留
      · 过时信息 (如"明天要考试") 自动淘汰
      · 最多保留最近 5 次会话的关键点
      · 总长度 ≤ 300 字
           │
           ▼
      新 rolling_summary (存入 student_profile 表)

示例演化:
  第1次后: "小红, 首次互动5/20。数学偏弱, 函数图像困难。"
  第3次后: "小红, 互动3次。数学偏科(几何好代数弱), 
           有考前焦虑, 情绪受成绩影响大。最近讨论函数图像。"
  第8次后: "小红, 老用户(8次)。数学偏科已有改善, 焦虑减轻。
           近期话题: 语文写作、同伴关系、期末考试准备。"
```

#### 2.5.8 关键设计决策

| 决策 | 结论 | 原因 |
|---|---|---|
| full 级别 L1 事实是否保留 | 清零，每次重新获取 | 事实数据可能过旧 |
| rolling_summary 更新时机 | 会话关闭时同步生成 | 下次会话可能在 Reflection 之前 |
| 关系强度注入方式 | 自然语言，放入人设增强包 | 不给 LLM 暴露"数字" |
| 归档摘要 vs Reflection | 归档摘要是会话级，Reflection 是认知级 | 两者不重复，各有用途 |

```
│        ┌──────────────────┐                                          │

```

```
│  Step 1: 存入 L3-Cold                              │
│  PostgreSQL JSONB, 同步写入, 不依赖 LLM             │

           │

┌──────────────────────────────────────────────────┐
│  Step 2: 小模型判断是否需要提取摘要                 │

│                                                   │
│  值得提取的条件 (任一命中):                          │

│  · 涉及心理状态变化 ("最近总是...")                  │
│  · Agent 回复中包含心理评估类内容                    │
│                                                   │
│  不值得提取:                                       │

│                                                   │

│           未命中 → 小模型二分类                     │

           │
      ┌────┴────┐
      │ 不值得    │ 值得
      ▼          ▼
   ┌────┐   ┌──────────────────────────────────┐

                       │

                ┌──────────────────────────────────┐
                │ Step 4: Schema 校验 + 兜底          │
                │                                   │
                │ Level 0: 完美提取 → 完整入库        │
                │   所有字段齐全, conf = 0.50         │
                │                                   │
                │ Level 1: 部分提取 → 打折入库        │
                │   emotion_primary 必填,             │
                │   其他可选字段为 null, conf × 0.8   │
                │                                   │
                │ Level 2: 极简提取 → 低分入库        │
```

#### 3.4.5 Cold 层生命周期

```
┌──────────────────────────────────────────────────────────────┐
│              Cold 层 (PG JSONB) 生命周期                       │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  Phase 1: 热归档期 (Day 0 ~ Day 30)                     │  │
│  │  · 所有原始对话完整保留                                  │  │
│  │  · 可以被 Hot 层回源                                    │  │
│  │  · 可用于摘要质量抽查、模型迭代重处理                     │  │
│  │  · 状态: active                                         │  │
│  └────────────────────────────────────────────────────────┘  │
│                         │                                    │
│                         ▼ Day 30                             │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  Phase 2: 温归档期 (Day 31 ~ Day 90)                    │  │
│  │  · 普通对话: 移出热表演, 进入温归档表                     │  │
│  │  · 危机/高重要性对话: 继续留在热表                       │  │
│  │  · 仍可通过 cold_ref 回源                               │  │
│  │  · 状态: warm_archive                                   │  │
│  └────────────────────────────────────────────────────────┘  │
│                         │                                    │
│                         ▼ Day 90                             │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  Phase 3: 删除期 (Day 91+)                              │  │
│  │  · 普通对话: 删除原文, 仅保留 L3-Hot 摘要                │  │
│  │  · Hot 层不受影响 (Milvus 摘要仍保留)                    │  │
│  │  · Hot.cold_ref → 置 null                               │  │
│  │  · 危机/高重要性: 永久保留原文                           │  │
│  │  · 状态: deleted / permanent                            │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  特殊规则:                                                    │
│  · crisis = true → 永久保留, 跳过所有过期阶段                │
│  · importance ≥ 0.7 → 延长至 180 天后删除                    │
│  · 被学生/辅导员主动标记 → 永久保留                          │
│  · 合规需求 → 学生可申请删除自己的原始对话                    │
└──────────────────────────────────────────────────────────────┘
```

#### 3.4.6 Hot-Cold 同步时序

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  写入时 (Cold 一定先于 Hot 存在):                              │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  Dialogue → Cold 写入 (同步, 拿 cold_id)              │   │
│  │         → LLM 提取摘要 (异步)                         │   │
│  │         → Hot 写入 (带 cold_id 回源指针)              │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  删除时 (Cold 删除不影响 Hot):                                 │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  Day 90 定时任务:                                     │   │
│  │    SELECT * FROM l3_cold                             │   │
│  │    WHERE created < now() - 90days                    │   │
│  │    AND crisis = false                                │   │
│  │    AND importance < 0.7                              │   │
│  │    → DELETE FROM l3_cold                             │   │
│  │    → Hot 的 cold_ref 字段置 null                      │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  异常同步:                                                    │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  Cold 成功 + Hot 失败:                                 │   │
│  │    Cold 标记 need_reprocess = true                    │   │
│  │    定时任务扫描 → 重试提取                              │   │
│  │                                                      │   │
│  │  Cold 失败:                                           │   │
│  │    整个 L3 链中断, 记录错误日志                        │   │
│  │    不影响对话回复 (L3 是后台异步链路)                   │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

#### 3.4.7 核心原则总结

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  ┌─────────────────────┐    ┌─────────────────────────────┐  │
│  │  L3-Hot (Milvus)     │    │  L3-Cold (PG JSONB)          │  │
│  ├─────────────────────┤    ├─────────────────────────────┤  │
│  │ 存: 结构化摘要        │    │ 存: 原始对话全文              │  │
│  │ 查: 每次检索都用       │    │ 查: 仅审计/抽查/重处理       │  │
│  │ 删: 跟遗忘衰减        │    │ 删: Day30温归档→Day90删除     │  │
│  │ LLM注入: YES         │    │ LLM注入: NO                 │  │
│  │ Reflection: YES      │    │ Reflection: 仅在重处理时     │  │
│  └─────────────────────┘    └─────────────────────────────┘  │
│                                                              │
│  1. Cold 先写, Hot 异步提取, 写入顺序不反过来                  │
│  2. Hot 挂了不影响 Cold, Cold 挂了是 PG 故障→整个系统停        │
│  3. 检索走 Hot, 审计走 Cold, 两条链路互不阻塞                  │
│  4. Cold 过期删除后 Hot 不受影响                              │
│  5. 提取失败有四级兜底, 最坏情况=没有 Hot, 系统仍能运行         │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 6.4 第三层：一致性置信度 (连续贝叶斯更新)

**更新公式**：

```
C_new = C_old + Δ

支持: Δ = quality × direction × novelty_decay × (1 - C_old)
反对: Δ = quality × direction × novelty_decay × C_old

其中:
  quality:       证据质量 (来自写入置信度)
  direction:     +1 支持 / -1 反对
  novelty_decay: e^(-0.01 × days_since_evidence)
  (1-C_old):     边际递减 — 越确信越难再提升
  C_old:         边际递减 — 越确信越容易被动摇(幅度大)
```

### 7.2 六种类型详细处理

```
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│  类型一: 直接对立 (Antonym Contradiction)                             │
│  ┌────────────────────────────────────────────────────────────────┐  │
│  │                                                                │  │
│  │  "讨厌语文" ⟷ "喜欢语文"                                        │  │
│  │                                                                │  │

│  │    1. 两条各降 0.2 (惩罚不确定性)                                 │  │

│  │    3. 每次新证据 → 贝叶斯连续更新                                 │  │
│  │    4. 一条收敛为强信念 (>0.85) → 另一条归档 (<0.30)               │  │
│  │    5. 30 天无新证据 → 双归档，承认不确定                          │  │
│  │                                                                │  │
│  │    置信度        收敛方向                                       │  │
│  │    0.8 ┤    ●──●──●──●  胜者→强信念                            │  │
│  │    0.5 ┤──●           ↘                                        │  │
│  │    0.2 ┤               ●──●──●  败者→归档                      │  │

│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  类型二: 时间覆盖 (Temporal Supersession)                             │
│  ┌────────────────────────────────────────────────────────────────┐  │
│  │                                                                │  │
│  │  "数学 72 分 (3月)" ⟷ "数学 89 分 (5月)"                        │  │
│  │                                                                │  │
│  │  处理流程:                                                      │  │
│  │    1. C_old 置信度不变，状态 → archived                         │  │
│  │    2. C_new 继承 C_old 的验证次数 +1                             │  │
│  │    3. 创建边 (C_old)-[:被更新]->(C_new)                          │  │
│  │    4. 检索默认返回最新的                                         │  │
│  │    5. "过去数学成绩"类查询可访问历史快照                           │  │
│  │                                                                │  │
│  │    (3月, 72分, active) ──被更新──→ (5月, 89分, active)           │  │
│  │      状态: archived                  置信度: 继承+升级           │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  类型三: 范围细化 (Scope Refinement)                                  │
│  ┌────────────────────────────────────────────────────────────────┐  │
│  │                                                                │  │
│  │  "数学偏弱" ⟷ "代数弱但几何很强"                                │  │
│  │                                                                │  │
│  │  处理流程:                                                      │  │
│  │    1. 不降权，不冲突                                             │  │
│  │    2. C_old 微降 0.05 (标记不够精确)                             │  │
│  │    3. C_new 置信度 = quality × 1.1 (奖励细粒度)                  │  │
│  │    4. 创建边 (C_new)-[:细化]->(C_old)                            │  │
│  │    5. 检索时两者都返回，LLM 自选粒度                              │  │
│  │                                                                │  │
│  │         ┌──────────┐                                           │  │

│  │         │ 0.65      │                                           │  │

│  │               │ 细化                                            │  │
│  │    ┌──────────┴──────────┐                                      │  │

│  │    │ 0.77     │  0.77    │                                      │  │
│  │    └──────────┴──────────┘                                      │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  类型四: 来源层级冲突 (Source Authority Conflict)                      │
│  ┌────────────────────────────────────────────────────────────────┐  │
│  │                                                                │  │
│  │  系统: "出勤率 62%" ⟷ 学生说: "我基本都去上课了"                  │  │
│  │                                                                │  │
│  │  处理流程:                                                      │  │
│  │    1. 不降权，不覆盖，并存                                       │  │
│  │    2. A 级标记权威源, S 级标记参考源                              │  │
│  │    3. 创建边 (C_system)-[:权威覆盖]->(C_self_report)             │  │
│  │    4. 做决策 → 以 A 级为准                                       │  │
│  │    5. 理解心理 → gap 本身就是信号                                 │  │
│  │       "学生认为自己出勤正常但实际 62%" = 有价值的诊断信息          │  │
│  │    6. 如果后续系统数据 + 自述都同向 → 自述可信度提升               │  │
│  │                                                                │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  类型五: 情绪波动 (Affective Fluctuation)                             │
│  ┌────────────────────────────────────────────────────────────────┐  │
│  │                                                                │  │
│  │  Day1: "好丧"  Day3: "挺开心"  Day5: "又不想上学了"              │  │
│  │                                                                │  │
│  │  处理流程:                                                      │  │
│  │    1. 不触发冲突消解                                             │  │
│  │    2. 不调整各自的置信度                                         │  │
│  │    3. 创建时序边记录波动                                         │  │
│  │    4. 同维度波动 ≥ 3 次 → Reflection 提炼波动元认知               │  │

│  │    5. 波动元认知的置信度随波动样本数递增                           │  │
│  │                                                                │  │
│  │    情绪                                                         │  │
│  │     ┤  ● (Day3: 开心)                                           │  │
│  │     ┤ ╱ ╲                                                       │  │

│  │     ┤     ╲    ● (Day5: 又丧了)                                  │  │
│  │     ┤      ╲  ╱                                                  │  │
│  │     ┤  ● (Day1: 丧)                                              │  │
│  │     └──┼────┼────┼────                                           │  │
│  │       Day1 Day3 Day5                                             │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  类型六: 语义重叠 (Semantic Overlap)                                  │
│  ┌────────────────────────────────────────────────────────────────┐  │
│  │                                                                │  │
│  │  "数学月考 72 分，很难过" ⟷ "这次月考数学砸了，才 72"            │  │
│  │  向量相似度 > 0.85，情感极性一致                                 │  │

│  │  处理流程:                                                      │  │

│  │    2. 保留最完整的表述                                           │  │
│  │    3. 合并置信度 = max(C_old, C_new) + 0.05 (奖励一致性)         │  │
│  │    4. 验证次数累加                                               │  │
│  │    5. 细节互补合并 (一条有分数, 一条有情绪)                        │  │
│  │                                                                │  │
│  │    "72分很难过"  ─┐                                            │  │
│  │                   ├─→ "数学月考 72 分，情绪低落"                 │  │
│  │    "砸了，才72"  ─┘    置信度 max + 0.05                         │  │

│                                                                      │
```

## 10. 关键技术约束备忘

- **心理安全熔断**：识别到自伤/重度抑郁关键词时，立即绕过黛玉人设，切换标准干预话术并通知辅导员
- **风格校准**：允许额外 LLM 调用成本用于 Self-Correction Loop，确保回复符合黛玉口吻（半文半白、避免客服用语）
- **情节预处理**：红楼文本需提前用 LLM 批量标注 `{scene, emotion, trigger, response_style, key_quote}`，构建情绪索引后再入库
- **Reranker 成本**：每条检索多一次 Cross-Encoder 调用（约 50-200ms），可接受
- **事实优先原则**：事实决定黛玉"说什么"，人格只决定"怎么说"。A 级系统数据永远覆盖 S 级用户自述
